# Fork Changelog (customizations)

1. **Group-scoped transfer matching** — accounts only auto-match within configured groups; the greedy matcher picks the closest-date pair across all accounts in the same group
2. **Per-family tuning knobs** — configurable date window and FX tolerance (defaults match upstream)
3. **Settings UI** — `/settings/transfer_match_groups` to manage groups and tuning
4. **Transfer detail panel** — shows each transaction's name and a "View transaction" link for both sides of a transfer
5. **Transfer match filter** — transactions page filter to show only auto-matched (pending) or confirmed transfer transactions
6. **Self-hosted build pipeline** — arm64 image to GHCR, auto-deploys via `sure-deploy`
7. ~~**Rule enrichment ignores locks**~~ — **reverted 2026-06-09**, now matches upstream: rules respect attribute locks. A manually-edited (locked) field — e.g. a category set from the UI — is no longer overwritten by rules on any path (sync, scheduled, or "apply all"). `enrich_attributes`' instance guard skips locked attributes regardless of `source` again, and `family/syncer.rb` applies rules without `ignore_attribute_locks`. The `ignore_attribute_locks` flag now only removes the executor's scope pre-filter; the instance guard still protects locked values.
8. **API: `kind` filter and update** — `GET /api/v1/transactions?kind=…` and `PATCH`/`POST /api/v1/transactions` with `kind` now supported; used by the provider-sync scripts to set native kinds at creation (`Contribution → investment_contribution`, `Withdrawal → funds_movement`). We follow stock Sure P&L semantics — there is no `kind`-reclassification housekeeping.
9. **Batch account sync after rule transfer creation** — `SetAsTransferOrPayment` now collects affected accounts and calls `sync_later` once per unique account after all transfers are built, instead of once per transaction, preventing N×2 sync explosions when rules apply to many transactions
10. **AI auto-categorization uses only subcategories** — `Family::AutoCategorizer` filters to subcategories only (`select(&:subcategory?)`), preventing assignment to parent/group categories
11. **Rule action: "Mark as transfer (no counterpart)"** — new `SetAsFundsMovement` action executor sets `kind: funds_movement` on matched transactions without creating a synthetic counterpart entry. Useful for single-leg transfers to untracked external accounts (off-ramps, external wallets).
12. ~~**"Investments Interest Returns" dashboard widget**~~ — **removed 2026-07-02**. Previously showed annualized interest yield (ARR) for interest-bearing investment accounts. Deleted `InvestmentInterestReturnsStatement`, its partial, and its locale file; removed the ivar and `build_dashboard_sections` entry from `pages_controller.rb`. No longer relevant once the vault/fund accounts moved to synthetic NAV holdings (earnings now show as portfolio return, not `Interest` transactions).
13. **"Investments Full" dashboard widget** — unrealized gains/losses for crypto holdings. Groups all current holdings across visible Investment+Crypto accounts by security, showing per-unit open price (avg cost) and current price, total cost basis (converted to family currency at avg cost), current market value, unrealized P&L (amount + %), and portfolio total P&L. Rows sorted by current value. Handles missing cost basis gracefully (shows "-" and a note). Also rolls up uninvested cash across the same accounts into a synthetic "Cash" row (cost basis == current value, so it never affects P&L $ amount), so the widget's total matches the native "Investments" widget's account-balance total (holdings + cash) instead of holdings-only. The total P&L **percent** is computed from holdings only (before the Cash row is added) to match the native widget's `unrealized_gains_trend`, which also excludes cash — otherwise cash's cost basis would dilute the percentage even though cash has zero gain. Only shown when at least one holding or nonzero cash balance exists. Modular/merge-safe: new `InvestmentsFullStatement` PORO + new `pages/dashboard/_investments_full` partial + dedicated locale file `config/locales/views/pages/investments_full/en.yml`; upstream touch is two small additions in `pages_controller.rb` (ivar + one `build_dashboard_sections` entry).
14. **"Currency breakdown" dashboard widget** — net worth distribution by account currency. Groups all visible accounts (included-in-finances for the current user) by their native currency, showing per-currency account count, native net total (assets minus liabilities), the same total converted to the family base currency at today's rates, and each currency's share of net worth (abs-weighted). Vehicle accounts are excluded. Only shown when more than one currency is present. Same modular/merge-safe shape as item 13: new `CurrencyBreakdownStatement` PORO + new `pages/dashboard/_currency_breakdown` partial + dedicated locale file `config/locales/views/pages/currency_breakdown/en.yml`; upstream touch is two small additions in `pages_controller.rb` (ivar + one `build_dashboard_sections` entry).
15. **Market data import split into two jobs** — Split the original 15-minute full-mode import into two separate scheduled jobs to fix retroactive valuation updates invalidating historical balances: (a) `import_market_data_today` runs every 15 minutes on weekdays (`*/15 * * * 1-5`) with `mode: today_only`, refreshing only today's prices/rates without touching historical data; (b) `import_market_data_full` runs once daily at market close (9 PM UTC / 5 PM EST, `0 21 * * 1-5`) with `mode: full`, handling end-of-day corrections and historical backfill. Per-account backfill (via `Account::Syncer`) remains unchanged. The split prevents mid-trading-day balance invalidation while preserving historical data correction capability. Per-security caching in `Security::Price::Importer` means most 15-minute runs are a no-op once a settled (non-provisional) price exists for the day.

16. **Sanity check for inverted balance query results** — `Balance::ChartSeriesBuilder` now includes a sanity check that detects when the SQL query returns start_balance > end_balance (which breaks balance continuity) and swaps them to restore correct trending. This workaround addresses an upstream bug in the complex LATERAL JOIN + FX conversion logic that occasionally inverts balance values in the charting query (issue #2052 territory). The fix is in the Ruby layer rather than SQL to minimize breaking changes; the root SQL bug should be addressed upstream.
17. **`sync-upstream` opencode skill** — `.opencode/skills/sync-upstream/SKILL.md` documents the rebase-onto-upstream-tag procedure (backup branch, rebase, known conflict spots, verify, push to main, deploy check, rollback) used to keep this fork current with `we-promise/sure`. Also requires re-diffing `sure-deploy/config/api_overrides.rb` against the upstream methods it copies before pushing to main, and smoke-testing the overridden endpoints after deploy: those `class_eval` overrides redefine whole methods, so upstream edits to them are discarded with no error and no merge conflict (an omitted `:type` in the trade permit list caused weeks of 500s on every API trade creation).

18. **Mobile horizontal scroll for fork widget tables** — the "Investments Full" and "Currency breakdown" widgets' table wrappers used `overflow-hidden` + `w-full` (copied from upstream's `investment_summary`), so on phones the table's min-content exceeded the card and got clipped with no scrollbar. Added `min-w-fit` to the inner table container (same approach as the native `balance_sheet` widget), so the outer `overflow-x-auto` scrolls the table horizontally on narrow screens. Desktop layout unchanged. Scoped to fork widgets only; native widgets untouched.
19. **Internal investment-to-investment transfers are `funds_movement`** — `Transfer.kind_for_account` accepts an optional `source_account:` and returns `funds_movement` (not `investment_contribution`) when both source and destination are Investment/Crypto accounts. Upstream inconsistency: `Transfer::Creator#outflow_transaction_kind` already guards this with `destination_is_investment? && !source_is_investment?`, but `kind_for_account` — used by auto-matching (`Family::AutoTransferMatchable`), the "Set as transfer" rule action, and manual UI matching — looked only at the destination, so moving money between two portfolio accounts was booked as new capital deployed and appeared as a P&L/budget expense. All three call sites now pass the outflow entry's account as `source_account:`. Default stays `nil`, so bank → investment is unchanged (`investment_contribution`).
20. **Regenerated `db/schema.rb` (GO-203)** — after the v0.7.3 sync, `db/schema.rb` was stale and missing the transfer-match schema: the `transfer_match_groups` / `transfer_match_group_memberships` tables and the `families.transfer_match_date_window` / `families.transfer_match_exchange_rate_tolerance` columns (fork migrations `20260530000000/1/2`). A fresh `db:prepare`/`db:schema:load` recorded those migrations as applied without running them, silently breaking auto-matching on any new DB. Regenerated `db/schema.rb` from a DB built purely from migrations (upstream v0.7.3 + fork), which also bumps the schema format to `ActiveRecord::Schema[8.1]`.

22. **Net worth / balance chart trend fix (supersedes the #16 sanity swap)** — the fork's item #16 "sanity check" in `Balance::ChartSeriesBuilder#build_series_for` swapped `current`/`previous` whenever a row's `start_balance` exceeded `end_balance`, assuming an inverted query. That heuristic misfired on legitimate declines and — critically — on stale `start_balance` values carried by archived/zeroed accounts (e.g. ARAS 1.0: start 11,692 / end 0, last row from 2022), inflating the dashboard Net Worth headline (~146k vs the true ~112k from the balance sheet). Fix: removed the swap; each series point's value/`trend.current` is now the true end balance, and `trend.previous` is the previous point's end value (first point flat) — matching `Series.from_raw_values` and upstream `gains_series` (SQL `LAG` self-fallback). The chart line's series values are unchanged; the balances-table `start_*` fields remain intact for the `Balance` model / reconciliation UI. Root-cause issue #2052 (inverted balance query) remains an upstream concern.
